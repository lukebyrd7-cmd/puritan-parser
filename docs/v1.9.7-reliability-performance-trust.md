# v1.9.7 — Reliability, performance, and trust audit

## Scope and release base

This release started from clean `main` at `4f9a217dad5605e5165a492b1ed492a8df42fdad`. After `git fetch origin --prune`, local `main` and `origin/main` matched. The starting commit is the merge of PR #82, `v1.9.6 — SRS Integrity & Runtime Reliability`; the v1.9.6 implementation commits `5bb35bf` and `53a6e47` are ancestors.

## Authoritative SRS behavior

Vocabulary state is authoritative per stable `lemma:<language>:<identity>` record in `pp_vocab_learning`. Status and mastery are separate. Review counts are derived from normalized recall events; `successCount` is only the active scheduler streak.

| Starting state or action | Result and schedule | Event/count behavior |
| --- | --- | --- |
| New | No record and no due date. Adding to Learning creates Learning with streak 0, interval 0, and due today. | `introduced` is not a review. |
| Learning | Streak 0 or an Again result. | Confidence ratings add exactly one review event. |
| Reviewing | Review-derived state with a positive streak below Known threshold. | Confidence ratings add exactly one review event. |
| Known through review | Review-derived streak at least 3; remains scheduled with a real due date. | Genuine recall history remains authoritative. |
| Manual Known | Known, `knownSource: manual`, streak 0, interval 0, due `9999-12-31`. | Adds `marked-known`, not fabricated recall. Existing genuine history is preserved. |
| Return to Learning | Learning, streak 0, interval 0, due on the learner's local calendar day. | Adds `introduced`; genuine prior recall history remains. |
| Again | Learning, streak 0, interval 1 day. | One missed/Again review event. |
| Hard | Streak is at least 1. Interval is `max(2, round(max(1,current) × 1.2))`, capped at 3,650 days. | One recognized/Hard event. |
| Good | Streak increments. Intervals are 3 days after the first success, 7 after the second, then `max(14, round(max(1,current) × 2))`, capped at 3,650. | One recognized/Good event. |
| Easy | Streak increments. Interval is `max(normal + 1, round(normal × 1.5))`, capped at 3,650. | One recognized/Easy event. |
| Maintenance SRS off | Status, source, streak, interval, due, and last scheduled review do not change. | One evidence event affects history/mastery. |
| Maintenance SRS on | Uses the same Again/Hard/Good/Easy scheduler. | One review event. |
| Recap | Evidence-only and excluded from Daily Practice. | Does not update the schedule. |
| Due work | A real due date on or before the learner's local day is due. The manual sentinel is never due. | Calculated from the authoritative record. |
| Session resume | The per-language session preserves cards, position, submitted event IDs, direction, and phase for seven days. | A submitted stable event ID/card cannot advance or write twice. |
| Needs attention | Independent per-language/per-ID marker used for candidate priority. | It does not change status, schedule, counters, or mastery by itself. |

Every accepted confidence transition writes the new status, streak, interval, due date, last-reviewed date, and event together in the returned record. The UI then checkpoints the vocabulary store and session; v1.9.6 rollback behavior keeps the card recoverable if persistence fails.

### Review history and counters

`reviewStatistics(record)` normalizes `recognized`/`missed` and confidence events into one population. Total reviews equals recognized plus missed. Successful reviews are Hard, Good, Easy, and legacy recognized events. Again/Hard/Good/Easy counters use that same population. Introduction and manual Known actions are not reviews. History is bounded to the model's compatibility limit, currently 200 events per vocabulary record. Latest review, last rating, Word Page counts, Daily Practice, and Progress all select from the same normalized events.

### Mastery

Mastery evidence weights are Again 0, Hard 0.45, Good 0.8, Easy 1.0; legacy recognized/missed score 1/0.

- F: last three events are misses, or at least four attempts with accuracy below 0.35.
- D: at least two misses in the last five, or at least four attempts with accuracy below 0.60.
- A: at least eight attempts, accuracy at least 0.90, active interval at least seven days, and no recent miss.
- B: at least five attempts, accuracy at least 0.68, and no more than one recent miss.
- C: every other state, including no evidence and manual Known without recall evidence.

Known therefore does not imply A. Maintenance evidence affects mastery whether scheduling is on or off. Return to Learning resets the active schedule but preserves genuine evidence.

## Findings and corrections

### Local-calendar due-date defect

Several scheduler, onboarding, DOM, and Progress paths derived a calendar date with `toISOString().slice(0, 10)`. That is a UTC date, so a learner west of UTC near local midnight could see tomorrow become due early, while a learner east of UTC could remain on yesterday. DST transitions made ad hoc millisecond shifting especially unsafe.

`src/core/calendar-date.js` now owns strict ISO-calendar parsing, local-day selection, and UTC-safe calendar arithmetic. All shared scheduling/date paths delegate to it. Tests cover leap day, US DST boundaries, negative shifts, invalid dates, Los Angeles before UTC midnight, and Kiritimati.

### Backup completeness defect

Export/import already preserved vocabulary rows, learning, Custom Decks, practice state, personal glosses, review targets, maintenance preference, Reader locations, and Reader display settings. It omitted saved vocabulary, appearance/preferences, and dashboard history. A valid settings-only profile was also rejected as empty.

Schema-4 export now includes those three domains. Import accepts and restores them, applies appearance without secondary writes, and reports unexpected parse/import errors to the console while retaining concise user copy. A deterministic populated round trip checks every intended domain.

### Preference-write duplication

Opening Settings called `applyTheme`, which saved preferences even when merely synchronizing controls. Bootstrap did the same on every launch. Theme/accent application now accepts `persist: false`; bootstrap, Settings synchronization, and import use it. A user-initiated theme/accent change still persists immediately. The round-trip test proves one preference write, not a save followed by theme/accent saves.

### Clear All omission

`pp_saved_vocabulary` was outside the central user-storage removal list. Clear All now removes it with the other local user domains. No key was renamed and no migration is required.

## Optimization decisions

Implemented high-value, low-complexity changes:

- one shared local-calendar implementation instead of repeated UTC/date arithmetic;
- no preference write during bootstrap, Settings rendering, or import-time visual application;
- reusable Search, SRS, and final-card benchmark commands;
- complete deterministic backup/restore surface.

Considered and intentionally rejected:

- splitting the vocabulary store into per-record keys: high migration/atomicity cost for no measured common-path need;
- prebuilding Search during startup: would move work into cold launch and Search already prepares in bounded chunks with 0.020 ms warm re-entry;
- caching full-history Progress aggregates across persistence: revision caches already exist and stale derived data would be a larger trust risk;
- changing Reader chapter caching or Reference rendering without a measured regression;
- broad listener framework/refactor: current roots are replaced/bounded and the change would exceed a hardening release's risk budget;
- any corpus, canonical-form, morphology, or gloss rewrite: integrity audits found no regression.
