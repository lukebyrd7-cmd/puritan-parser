# v1.9.4 — PWA Offline Reliability & Startup Performance

## Release scope

This release addresses the physical iPhone installed-PWA failure in which the cached application shell opened offline but Reader, Learn, Reference, and Settings did not respond. It also addresses the cold preparation delay in Vocabulary Search and Learn / Daily Practice. The starting `main` commit was `02ad1f716126347ff7b253177e2ff9ffb3a4eb8f` (v1.9.3).

No biblical corpus or lexical definition was changed. No persisted-data migration was added.

## Root causes

### Offline shell without navigation

The v1.9.3 service worker cached `main.js` and the stylesheet with their version query, but cached almost every dynamically injected JavaScript module only without a query. `main.js` always requests those modules with `?v=v1.9.3-bilingual-lexical-completion-1`, while the service worker deliberately required an exact cache match for versioned JavaScript and CSS. During a cold offline launch:

1. cached `index.html` and cached versioned `main.js` opened;
2. versioned core-module requests missed the cache;
3. network fetches failed;
4. the generic static fallback could return `index.html` for a JavaScript request;
5. core startup never completed, so `wireEvents()` never bound the already-visible navigation buttons.

That exact URL mismatch explains why the shell appeared while taps did nothing. It is not iOS-specific, although the standalone iPhone cold launch exposed it reliably.

Large runtime JSON was also network-first and cached only after use. Consequently, even a correctly booted app could not open unvisited chapters, Search data, lexical glosses, or interlinear details offline. Network-first JSON could also wait on a failed request before consulting cache.

### Search cold path

The dominant cold costs were the 18 MiB `vocab_all.json` fetch/parse, normalization and SRS preparation of 75,852 form rows, lemma grouping into 14,630 searchable entries, the Hebrew lexical-gloss parse, searchable/transliteration field creation, sorting, token-index construction, and user-state decoration.

A direct cold Search could begin preparing against empty app data before shared vocabulary hydration finished, then render again and build the real corpus after hydration. Search, Learn, and Reader also owned separate Hebrew-gloss fetch/promise caches, so route changes could re-fetch and re-parse the same 3 MiB asset.

### Learn cold path

Learn correctly deferred its dashboard summary, but still had to wait for shared vocabulary hydration before rendering real practice controls. Its dashboard groups both language datasets and computes due, ready-learning, and daily-plan summaries. Hebrew practice separately loaded the same Hebrew gloss map used by Search and Reader. First-use practice also sorted the entire eligible New-word pool merely to choose five entries.

The offline navigation failure and CPU-heavy Search/Learn preparation were independent primary defects. They overlapped in two secondary ways: required data was not installed ahead of time, and network-first JSON made offline preparation wait for a failed network attempt. Fixing the module cache mismatch restores navigation; shared preparation and cache-first installed data address the cold feature paths.

## Service-worker and offline design

Cache identifier: `puritan-parser-v110-v1.9.4-pwa-offline-reliability-1`.

Installation creates one version-specific cache and must finish every required asset before the new worker activates. It caches exact-version URLs for every script requested by `main.js`; JavaScript misses never fall back to HTML. Activation deletes only obsolete `puritan-parser-*` caches and does not touch localStorage, IndexedDB, learning state, settings, personal glosses, or Reader locations.

The service worker reads the committed Greek, Hebrew, Hebrew-interlinear, OEB, and WEB manifests and expands their chapter lists deterministically. Assets are fetched in bounded batches of 24. App navigations resolve cache-first to `index.html`. Installed core JSON is cache-first, so expected offline operation never begins with a failing network request. An uncached same-origin runtime asset can still be fetched and cached; cross-origin fonts remain intentionally network-only and fall back to local fonts offline.

## Shared preparation and interaction feedback

`loadLexicalGlossMap()` is now the single promise/cache for each language. App hydration, Search, Learn, and Reader reuse it. A shared runtime-preparation coordinator single-flights language lemma grouping, lexical gloss preparation, and Search preparation.

After vocabulary hydration and the first interactive render, an idle task prepares the active language first, the other language second, then the reusable Search structures. Opening Search before idle warmup completes takes priority through the same promises; no duplicate job is created. Work stays chunked and local. Search now waits for real app data instead of building an empty cold index, and shows the accessible status `Preparing search…`. Learn already renders `Preparing your learning library…` during initial hydration and replaces a selected action with `Preparing … practice…` before session assembly. Top-level navigation remains available throughout.

First-use Learn selection now maintains only the best five eligible New words instead of sorting the complete eligible pool. Ordering and Daily Practice semantics are unchanged.

## Measurements

Measurements used the same static production build through `serve -s`, a fresh local origin, cold page navigation, and browser performance instrumentation. They are diagnostic samples, not CI timing assertions.

| Measurement | v1.9.3 baseline | v1.9.4 final |
| --- | ---: | ---: |
| App/Search shell interactive | 488.4 ms | 557.1 ms |
| Search navigation to prepared index/results | 4,411.6 ms | 1,962.9 ms |
| Search first query to rendered results | 3.3 ms | 1.7 ms |
| Search warm query to rendered results | 2.4 ms | 3.1 ms |
| Learn navigation to first primary control | 425.1 ms | 486.8 ms |
| Learn navigation to completed dashboard summary | 657.8 ms | 765.8 ms |
| Learn first-use click acknowledgment | 8.8 ms | 1.4 ms |
| Learn click to first actionable card | 45.4 ms | 47.3 ms |

The Search cold path improved by about 2.45 seconds because empty/duplicate cold preparation and repeated gloss initialization were removed. Query times remain a few milliseconds. App-shell and Learn samples varied by tens of milliseconds and did not show a material cold-path speedup; they also did not move Search work synchronously into startup. The visible preparation states and sub-frame action acknowledgment address the “dead button” symptom while background warmup improves the common route-transition case.

Structural counters enforce one Search corpus build, one shared lexical map load per language, one language-grouping job per data revision, and one concurrent warmup job.

## Validation

Automated v1.9.4 coverage models online installation, activation, total network loss, cold navigation routes, exact-version module fetches, representative Greek and Hebrew chapters, bilingual Search indexes, Hebrew interlinear Word Details data, both translation providers, and a second offline cold launch. Existing Reader, Word Page, Search, Learn, Reference, Settings, routing, local persistence, and bilingual integrity suites remain part of the full test run.

The in-app browser completed cold online performance checks without console errors. A literal disconnected-localhost browser reload could not be inspected because the browser-control security policy blocks unreachable local URLs. Total network loss is therefore covered deterministically by the service-worker harness; physical installed-iPhone verification remains required after deployment.

Hebrew interlinear integrity remains 934 files with aggregate SHA-256 `dab7552afccf0b9916cd3bd77b83843462bdb20f9eb58f1cfa1a67fbb6a4ee39`. `vocab_all.json` remains byte-for-byte unchanged at SHA-256 `1d62bdcf3bd2d33e945bcd499f9edbf6dd680b928c784b228c02db052eea5a64`.

## Physical iPhone retest after deployment

1. With networking enabled, open the production site in Safari and leave it open until the release has loaded; reload once so the new worker controls the page.
2. Install with **Add to Home Screen** and **Open as Web App**, or relaunch the existing installed app after the online update.
3. Confirm Reader, Learn, Search, Reference, and Settings once online. It is not necessary to visit individual chapters.
4. Fully close the installed app.
5. Enable Airplane Mode and separately disable Wi-Fi.
6. Cold launch from the Home Screen and test Learn, Greek Reader and Word Details, Hebrew Reader and Word Details, Greek and Hebrew Search, Reference, Settings, and one local setting/Reader-position change.
7. Fully close the app while still offline, relaunch it again, and confirm the saved setting and Reader positions remain.
8. Record any blank state, nonresponsive control, console diagnostic available through Safari Web Inspector, and the exact route/data item involved.
